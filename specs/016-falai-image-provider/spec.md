# Feature Specification: fal.ai Image-Generation Provider — Pluggable Alongside Gemini

**Feature Branch**: `016-falai-image-provider`
**Created**: 2026-05-05
**Status**: Draft
**Input**: GitHub issue [#40 — Replace current image generation model with fal.ai model](https://github.com/squer-solutions/ai-codecrafts-alterego/issues/40). Exact request: *"Replace the current AI Image Generation model with fal.ai one. Java API docs could be found here https://fal.ai/models/fal-ai/nano-banana-pro/edit/api?platform=java. All the other logic should remain the same. Previous model should not be removed from the code. There should be a configuration introduced to choose which model is going to be used, for example, through spring_profiles_active."*

> **Relationship to earlier features.** This feature **extends** 003-gemini-image-generator (the current real-provider image path) by adding a **second** real provider — fal.ai's `nano-banana-pro/edit` image-edit model — without removing the Gemini provider. The choice of which real provider runs at any given time is a runtime configuration switch (e.g. Spring profile), not a code change. Every other behaviour established by 001 / 002 / 003 / 008 / 015 (tabbed layout, Setup form, Generate gating, photo reduction before upload, fallback-on-failure, no-persistence, generic fallback notice, branding logos, branded poster frame) is preserved unchanged. The fallback path (001 FR-018 → 003 FR-212/214) continues to be the stub poster from 001 — fal.ai becomes the second of two **real** sources, with the stub remaining the universal fallback.
>
> Concretely, when an operator selects the fal.ai provider, the user-visible flow is **identical** to a Gemini run; only the upstream HTTP call differs. The poster, the loading indicator, the generic fallback notice, the WCAG behaviour, and the response shape consumed by the frontend are all the same.

## Clarifications

### Session 2026-05-05

- Q: When both real providers are configured (both API keys present), which one runs? → A: **The active profile chooses exactly one.** The configuration mechanism (Spring `spring.profiles.active` or equivalent) is the single source of truth — not "first key found", not "fail if both set". Selecting `gemini` runs Gemini even if a fal.ai key is also exported; selecting `falai` runs fal.ai even if a Gemini key is also exported. If neither real-provider profile is active, the system runs the 001 stub (current `default` profile behaviour) — not fal.ai by default. This keeps the 003 invariant that "missing config falls back without erroring" and adds: "ambiguous config does not produce ambiguous behaviour".
- Q: Should the response metadata grow a new field so operators can tell which real provider produced a `outcome: "real"` poster? → A: **Yes — extend with a `provider` discriminator.** 003 FR-218 today exposes `outcome` (`"real"` / `"fallback"`) and, on fallback, a `reason` code. With two real providers in the codebase, that is no longer enough to verify "did the run actually go through the provider I configured?" without a code inspection. Add a `provider` field whose values are `"gemini"`, `"falai"`, or `"stub"`, set on every Generate response, so operators can confirm provider selection from devtools alone. This is operator-visible only — the user-visible UI does NOT surface it (the generic fallback notice from 003 FR-214 remains the only end-user signal).
- Q: When the fal.ai provider is selected but is unavailable (no key, network error, timeout, malformed response, safety refusal, queue stall), what does the user see? → A: **Identical to the Gemini fallback experience from 003.** The same generic, single-variant, non-blaming notice ("Showing a preview image — live AI generation isn't available right now."), the same stub poster underneath, the same set of operator-visible reason codes (`not_configured` / `network_error` / `rate_limited` / `timeout` / `malformed_response` / `safety_refused`), the same flow continuation (Start over, Generate again work). The user MUST NOT be able to tell which real provider was attempted from the UI — this is a deliberate parity choice so a partial outage of either provider degrades to the same UX.
- Q: What happens at startup when both `gemini` and `falai` profiles are active simultaneously (a misconfiguration)? → A: **Refuse to start with a clear, fatal log line.** No silent precedence, no alphabetical tiebreaker, no "first listed wins". The backend MUST log a fatal error naming both active real-provider profiles and exit non-zero. The operator is forced to pick exactly one before the process will run. Rationale: a silent precedence rule looks fine in review but causes confused incidents when an operator believes they switched to fal.ai while Gemini is quietly serving (or vice versa). The 001/003 baseline already favours "fail loud at startup" over "guess and proceed".
- Q: On a fallback response, should the response body disclose which real provider was *attempted* (e.g. an `attemptedProvider` field), or should the `provider` field describe only what actually served the response? → A: **`provider` describes what actually served, full stop.** The response body's `provider` field always names the path that produced the central image of *this* response: `"gemini"` / `"falai"` for a real success, `"stub"` on every fallback (regardless of which real provider was attempted-and-failed). No `attemptedProvider` field is added. Diagnostic detail about which real provider was attempted on a fallback lives in the FR-1613 structured log line, never in the HTTP response. Rationale: keeps the response schema small and unambiguous (one field = one fact), preserves additive compatibility with 003 (the only addition is the `provider` field), and avoids leaking attempt-history into the frontend's reach.
- Q: What is the user-visible upper bound on the wall-clock wait when fal.ai's queue is slow, before the backend gives up and serves the stub fallback? → A: **30 s end-to-end** (request submission → subscribe/poll → terminal status → image bytes resolved), measured from the moment the backend receives the user's `POST /api/generate` until it either has the fal.ai-generated image bytes ready to return or transitions to the stub fallback path. After 30 s with no terminal success the backend MUST stop waiting on fal.ai and respond with the stub poster, `outcome: "fallback"`, `reason: "timeout"`. This bound is across the entire fal.ai exchange (including any retries, back-off pauses, queue-acquire, and subscribe wait) — it is not a per-attempt timeout. Rationale: aligns with the 013 progress indicator's 20 s "100 %" mark plus a 50 % buffer (worst-case "stuck on 99 %" wait of ~10 s) and matches 003's 25 s per-call ceiling for Gemini plus a small queue-acquire allowance. Anything past 30 s is overwhelmingly a stall rather than a slow-but-healthy run; falling back keeps the flow usable.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Run the same generation flow against fal.ai instead of Gemini, by configuration alone (Priority: P1)

An operator (the person who runs the backend at the demo / for development) wants to switch the live image-generation provider from Gemini to fal.ai. They do not want to redeploy a different binary, edit Java source, or recompile — they want to set a configuration value (e.g. `SPRING_PROFILES_ACTIVE=falai`, plus a fal.ai API key) and restart, and have the next user's Generate press route through fal.ai's `nano-banana-pro/edit` model. The end user, using the same browser session, does not see anything change in the UI — they still complete the Setup form, press Generate, see the loading indicator on the "Your Alter Ego" tab, and receive a poster anchored to their photo.

**Why this priority**: This is the core ask of the issue. Without this, the feature is not delivered.

**Independent Test**: Start the backend with the fal.ai profile active and a valid fal.ai API key. Complete the Setup form end-to-end in the frontend and press Generate. Observe a poster whose central image was returned by fal.ai (verifiable via the `provider: "falai"` field on the response and via a backend log line). Repeat with a different role / universe combination and confirm the poster's central image is visibly different — i.e. Setup inputs reach fal.ai, not just an unconditioned model.

**Acceptance Scenarios**:

1. **Given** the backend is started with the fal.ai provider selected (e.g. `SPRING_PROFILES_ACTIVE=falai`) and a valid fal.ai API key configured, **When** the user completes the Setup form and presses Generate, **Then** the app auto-switches to "2 Your Alter Ego" (per 002 FR-108), the loading indicator renders, and on success the poster's central image is the one fal.ai returned for this (photo, pose, archetype, universe, vibe, name, art style) combination — and the response metadata reports `provider: "falai"`, `outcome: "real"`.
2. **Given** the backend is started with the Gemini provider selected (e.g. `SPRING_PROFILES_ACTIVE=gemini`) and a valid Gemini API key configured, **When** the user runs Generate, **Then** the existing 003 behaviour is preserved end-to-end — the response metadata reports `provider: "gemini"`, `outcome: "real"`, and the user-visible flow is unchanged from the 003 baseline.
3. **Given** the backend is started with **no** real-provider profile active (i.e. the `default` profile, the current 001 behaviour), **When** the user runs Generate, **Then** the stub image is served, the response metadata reports `provider: "stub"`, `outcome: "fallback"`, `reason: "not_configured"`, and the user sees the generic fallback notice (003 FR-214). Selecting *no* real provider MUST NOT default to fal.ai.
4. **Given** the operator changes only the configured provider between two backend restarts (Gemini → fal.ai), with all other inputs (photo, Setup selections) held identical, **When** the user runs Generate against each, **Then** both runs return a complete poster — the *user-visible UI* is indistinguishable across the two runs (same loading indicator, same poster slot, same fallback notice copy if either fails), but the response metadata's `provider` field differs and a backend log line records the selected provider.
5. **Given** the user's photo is large (e.g. a phone capture above several megabytes), **When** they press Generate against the fal.ai provider, **Then** the same backend photo-reduction step that runs for Gemini (003 FR-206..209) runs for fal.ai — the photo is brought within fal.ai's documented per-request size limits before the outbound call, so the request is not rejected for payload-size reasons.

### User Story 2 — All my Setup inputs still shape the generated image when fal.ai is the provider (Priority: P1)

The user's pose, archetype, universe, vibe (when selected), first name, art style, and photo all visibly influence the fal.ai-generated image — exactly as 003 FR-203 / User Story 2 of 003 already requires for Gemini. Switching providers MUST NOT regress the "every Setup input matters" property.

**Why this priority**: Without this, switching providers silently degrades the feature. 003 explicitly required all Setup inputs to influence the image; that property must hold under fal.ai too.

**Independent Test**: Run the same A/B matrix used by 003 SC-202 (vary one axis at a time — role, universe, pose; then swap the photo — across pairs of runs with all other inputs held constant) but against the fal.ai provider, and confirm pairwise visible differences in the generated images.

**Acceptance Scenarios**:

1. **Given** two fal.ai-backed Generate runs that differ only in **archetype** (e.g. Backend Dev vs. Cloud Architect) with all other inputs identical, **When** both runs complete successfully, **Then** the two generated images show role-appropriate differences (props, attire, setting cues) rather than being identical or indistinguishable.
2. **Given** two fal.ai-backed Generate runs that differ only in **universe** (e.g. Cyberpunk vs. The Office) with all other inputs identical, **When** both runs complete successfully, **Then** the two generated images show universe-appropriate aesthetic differences.
3. **Given** two fal.ai-backed Generate runs that differ only in **pose** (e.g. Heroic vs. Scholar) with all other inputs identical, **When** both runs complete successfully, **Then** the two generated images show visibly different stances consistent with the selected pose.
4. **Given** two fal.ai-backed Generate runs that differ only in **art style** (e.g. oil painting vs. pixel art — per 006), **When** both runs complete successfully, **Then** the two generated images render in the corresponding aesthetic — the art style enum reaches the model.
5. **Given** two fal.ai-backed Generate runs with the same role/universe/pose/style but different users' photos, **When** both runs complete successfully, **Then** each generated image's face anchors to its own user's photo (the two outputs are not interchangeable and do not depict the same person).
6. **Given** a fal.ai-backed Setup run with **vibe** selected and one without (same other inputs), **When** both runs complete successfully, **Then** the vibe's presence modulates the generated image (tone, mood, or accent) — the two outputs are not identical. *(When vibe is absent, the image remains coherent; vibe is a modulator, not a gate, per 002.)*

### User Story 3 — Graceful degradation when fal.ai is unavailable (Priority: P2)

When fal.ai is selected but cannot serve the request — no API key configured, network error, timeout, queue stall, rate limit, an explicit error response, a malformed image payload, or a safety-filter refusal — the user still sees a complete poster (the 001 stub) and the same generic, non-blaming, non-blocking fallback notice the user would see for a Gemini failure. The flow stays usable: Start over and Generate again continue to work; subsequent successful fal.ai runs render real images normally.

**Why this priority**: This is resilience behaviour. 001 FR-018, constitutional Principle IV, and 003 FR-214 together already mandate this baseline for the Gemini path; the fal.ai path MUST NOT regress it. P2 because the property already exists on the Gemini path — the work here is confirming the new provider preserves it.

**Independent Test**: Simulate fal.ai-side failure modes one at a time — (a) no fal.ai key configured under the fal.ai profile, (b) network error reaching fal.ai, (c) fal.ai returns an explicit error / queue-failed response, (d) fal.ai response is malformed (non-image content, truncated), (e) fal.ai returns a safety refusal — and confirm in each case the user receives a complete fallback poster + the same generic notice, the response carries `outcome: "fallback"` with a reason code from the FR-218 enumeration, the response carries `provider: "stub"`, and the flow continues to work.

**Acceptance Scenarios**:

1. **Given** the backend is started with the fal.ai profile active but **no fal.ai API key** configured, **When** the user presses Generate, **Then** the poster renders successfully using the 001 stub image, the response metadata reports `provider: "stub"`, `outcome: "fallback"`, `reason: "not_configured"`, and the user sees the generic fallback notice — the run MUST NOT block further use.
2. **Given** the fal.ai API call **times out, fails after retries, queues but stalls past the configured wait, returns an HTTP error, returns a malformed image response, or is refused by fal.ai's safety filter**, **When** the client receives the response, **Then** the poster still renders with the stub image, the metadata reports `provider: "stub"`, `outcome: "fallback"` and a `reason` code drawn from the FR-218 enumeration, and the user-visible notice is identical to the one shown for any other fallback (no provider name, no reason exposure).
3. **Given** a fal.ai-backed fallback poster has just been rendered, **When** the user presses Start over and runs Generate again under healthy fal.ai conditions, **Then** a real fal.ai-generated poster appears on the successful re-run (no persistent error state is carried forward; the metadata transitions from `provider: "stub"` to `provider: "falai"`).
4. **Given** any run (real-provider success or fallback), **When** the run completes, **Then** the loading→poster (or loading→fallback poster + notice) transition is announced to assistive technologies via ARIA live regions per 001 FR-022 — unchanged from 003.

### Edge Cases

- **Both real-provider keys exported in the environment, only `falai` profile active.** Per the clarification above, the active profile wins. The system runs fal.ai; the Gemini key is ignored. Reverse direction is symmetric.
- **Both `gemini` and `falai` profiles activated simultaneously** (e.g. `SPRING_PROFILES_ACTIVE=gemini,falai`). Per FR-1605, the backend MUST refuse to start: it logs a fatal error naming both profiles and exits non-zero. There is no precedence rule, no silent fallback to one of them, and no race — the operator must remove one profile and restart.
- **fal.ai's `nano-banana-pro/edit` model identifier moves or is renamed** at the provider. Per FR-1610, the identifier is configurable — operators re-point without a code change.
- **fal.ai uses an asynchronous queue / subscribe pattern** rather than a single synchronous call. The user-visible behaviour MUST be unchanged: the loading indicator from 002 / 013 (the existing pulsating disc with live percent count-up) keeps running until the final image is available, then transitions to the poster reveal. The provider's queue mechanics are not exposed to the end user. Per FR-1614a, the entire exchange (submit → queue → subscribe → image bytes) is capped at 30 s wall-clock end-to-end, after which the backend abandons the fal.ai run and serves the stub fallback with `reason: "timeout"`. The 013 indicator's "100 %" mark at 20 s means a worst-case slow-but-healthy fal.ai run leaves the user on "99 %" for up to 10 s before the poster appears; a stalled run leaves them there for at most 10 s before the fallback poster appears.
- **fal.ai returns the image via a CDN URL** rather than inline base64. The backend MUST resolve the URL to actual image bytes before responding to the frontend, so the frontend's image slot does not become coupled to a third-party CDN. The response shape consumed by the frontend MUST be unchanged from 003.
- **fal.ai's photo size / pixel-edge limits differ from Gemini's.** The photo-reduction step (003 FR-206..209) MUST be tuned per-provider so each provider's documented limits are respected. Reduction parameters MUST be configurable per provider.
- **Operator switches provider mid-session** (restarts backend with different profile while a frontend session is open). The next Generate press flows through the new provider; any in-flight run from before the restart is treated as failed and follows the fallback path (consistent with 001 / 003).
- **Rate-limit / quota exhaustion on fal.ai.** Treated identically to the Gemini rate-limit case — fall back to the stub poster with the same generic notice; metadata reason `rate_limited`.
- **Backend process is killed mid-run.** Inherits 001 / 003 — the in-flight request is lost; the user's next Generate starts a fresh run.
- **Latency profile differences between providers.** The 013 progress indicator (linear count-up to 99%, mapped to 20 s) is unchanged. Whether fal.ai is faster or slower than Gemini in practice is a planning / observability concern, not a spec-level UX change.
- **fal.ai client library availability for Java.** The provider's Java API page is the documented entry point. The choice of integration mechanism (raw HTTPS calls vs the published Java helper) is a planning-phase decision constrained by the project's existing "no third-party SDK in production business code" preference; the spec requires only that the integration is testable and follows the resilient-HTTP policy.

### Functional Requirements

**Pluggable provider selection**

- **FR-1601**: The backend MUST support **two** real image-generation providers simultaneously present in the codebase: the existing Gemini integration (003) and a new fal.ai integration targeting the `nano-banana-pro/edit` image-edit model. Adding the fal.ai integration MUST NOT remove, hide, or otherwise regress the Gemini integration — the Gemini path remains buildable, runnable, and testable in the same artefact.
- **FR-1602**: The choice of which real provider runs at process start MUST be controlled by a runtime configuration switch (e.g. Spring `spring.profiles.active`). The selection MUST be possible without a code change: changing only an environment variable / profile and restarting the backend MUST be sufficient to swap the live provider.
- **FR-1603**: When **no** real-provider profile is active (the `default` profile case), the system MUST continue to serve the 001 stub for every Generate request — exactly as it does today — and MUST NOT spontaneously route to either real provider. The default behaviour stays "stub-only", consistent with 001 / 003.
- **FR-1604**: When the active profile selects a real provider but that provider's API key is not configured, the backend MUST start successfully and every Generate request MUST fall back to the 001 stub with the existing generic fallback notice and a `reason` of `not_configured` — exactly the behaviour 003 FR-212 already mandates for Gemini. This MUST hold for fal.ai too.
- **FR-1605**: When more than one real-provider profile is activated simultaneously (e.g. `SPRING_PROFILES_ACTIVE=gemini,falai`), the backend MUST refuse to start. It MUST log a fatal error message that names both active real-provider profiles and exit with a non-zero status code, before serving any Generate request. The backend MUST NOT silently apply a precedence rule, race the two providers, fan out to both, or pick non-deterministically per-request. The operator is required to remove one of the two profiles from `spring.profiles.active` (or the equivalent configuration source) before the process will start.

**fal.ai-specific image generation**

- **FR-1606**: When the fal.ai provider is selected and configured, the backend MUST, on every successful Generate run, send the user's photo plus every Setup-form field (pose, archetype, universe, first name, vibe when provided, art style) to fal.ai's `nano-banana-pro/edit` image-edit model and use the returned image as the central image of the generated poster. The text payload composed for fal.ai MUST include the user's first name so personalisation reaches the image.
- **FR-1607**: The Setup inputs that 003 FR-203 already required to "measurably influence" the Gemini image — pose, archetype, universe, vibe (when present), first name, art style, and photo — MUST measurably influence the fal.ai image too. "Measurably influence" means: changing one input while holding the others constant produces a visibly different image across typical runs.
- **FR-1608**: The fal.ai-generated image, once received, MUST be rendered on the "Your Alter Ego" tab in the same slot occupied today by the Gemini / stub image, with no additional user-visible chrome introduced by this feature. The fallback notice from 003 FR-214 remains the only permitted user-visible addition, and only when a fallback occurs.
- **FR-1609**: The fal.ai-generated image MUST flow through the same downstream poster-composition pipeline already used for Gemini and stub images — including the logo overlay (008) and the branded poster frame (015) — so the user-facing output (poster look-and-feel, dimensions, accessible markup) is identical regardless of which real provider produced the central image.

**Configuration, credentials, and provider policy**

- **FR-1610**: The fal.ai model identifier (default: `fal-ai/nano-banana-pro/edit`), the fal.ai endpoint URL, and any request parameters needed to reach the model MUST be backend configuration inputs rather than hard-coded values, mirroring the way 003 FR-210 makes Gemini's identifier configurable. The default identifier MUST match the one referenced in the issue unless that identifier is not reachable at the provider, in which case a currently-reachable fal.ai image-edit model is substituted and the substitution is recorded in the planning documents.
- **FR-1611**: The fal.ai API key MUST be read by the backend from a runtime configuration source (environment variable or equivalent — e.g. `FAL_AI_API_KEY`), separately from the Gemini key. The frontend MUST NOT transmit, read, or store the fal.ai key, and the key MUST NOT appear in logs, responses, or error messages surfaced to the browser. The two real-provider keys MUST be independently configurable (presence of one MUST NOT depend on or imply presence of the other).
- **FR-1612**: The backend response for every Generate run MUST include a `provider` discriminator with one of three values: `"gemini"`, `"falai"`, or `"stub"`. The value MUST reflect which path actually produced the central image of this specific response: `"gemini"` for a real Gemini success, `"falai"` for a real fal.ai success, `"stub"` for any run where the fallback path served the image (for any reason — not configured, network error, etc.). The existing `outcome` and `reason` fields from 003 FR-218 keep their semantics unchanged: `outcome: "real"` when `provider ∈ {"gemini", "falai"}`, `outcome: "fallback"` when `provider == "stub"`. The response body MUST NOT carry any additional field disclosing which real provider was *attempted* on a fallback (no `attemptedProvider`, no `failedProvider`); that information lives only in the FR-1613 log line. The `provider` field is **operator-visible only** — the frontend MUST NOT render it in the user-visible UI, and the user-visible fallback notice MUST remain the generic, single-variant 003 FR-214 message.
- **FR-1613**: The single structured log line per Generate run mandated by 003 FR-219 MUST record both (a) the `provider` value that served the response (`gemini` / `falai` / `stub`) — matching the response body's `provider` field — and (b) when the served provider is `stub`, the real provider that was *attempted-and-failed* (`gemini` / `falai`) **or** the value `none` if no real provider was attempted because the runtime selection resolved to "no real provider configured" (the 001 default-profile case). This makes the log line the single source of truth for "which real provider was attempted on a fallback", since FR-1612 forbids putting that information in the HTTP response. The log line MUST NOT include the photo bytes, either provider's API key, or the raw error payload of either provider.
- **FR-1614**: Outbound calls from the backend to fal.ai MUST follow the project's resilient-HTTP policy (multiple attempts with back-off and randomised jitter) per 001 FR-019 / constitutional Principle IV. Number of attempts and back-off bounds MUST be configurable per provider. *(Rationale: providers have different latency / error profiles; coupling them to a single global retry budget is unhealthy.)*
- **FR-1614a**: The total wall-clock time the backend spends on a single fal.ai exchange — measured from receipt of the user's `POST /api/generate` to the moment fal.ai's image bytes are in hand or the request is abandoned — MUST be capped at **30 seconds**. The cap MUST cover the full exchange (initial request submission, queue-acquire, subscribe / poll loop waiting for terminal status, retries with their back-off pauses, and final image-bytes resolution); it MUST NOT be expressed only as a per-attempt timeout that resets on each retry. The 30 s value MUST itself be a configurable parameter so it can be tuned per environment, but its default MUST be 30 s. When the cap is reached without a terminal success, the backend MUST stop waiting on fal.ai and serve the stub fallback with `outcome: "fallback"`, `reason: "timeout"`, `provider: "stub"`.
- **FR-1615**: When the fal.ai call ultimately fails — after retries exhausted, on timeout, on rate-limit / quota response, on malformed or non-image payload, on safety refusal, or when not configured (FR-1604) — the response MUST render a complete fallback poster using the 001 stub image and the UI MUST surface the **identical** generic single-variant notice already shown for Gemini failures (003 FR-214). The notice MUST NOT name fal.ai (or Gemini) to the end user, MUST NOT disclose the specific reason, MUST be programmatically announced per 001 FR-022/023, and MUST NOT block subsequent interactions. The set of operator-visible reason codes MUST be drawn from the same fixed enumeration as 003 FR-218 (`not_configured` / `network_error` / `rate_limited` / `timeout` / `malformed_response` / `safety_refused`); fal.ai-specific failure modes (e.g. queue stall) MUST be mapped onto that same enumeration rather than introducing new user-visible codes.

**Photo handling under fal.ai**

- **FR-1616**: Before sending the user's photo to fal.ai, the backend MUST reduce the photo's size (pixel dimensions and/or encoded byte size) when it exceeds a sensible threshold tuned to fal.ai's documented per-request and per-image limits, exactly as 003 FR-206..209 already requires for Gemini. The reduction threshold MUST be a configurable parameter independent of Gemini's threshold (since the two providers have different limits), and MUST preserve enough visual fidelity for the model to anchor the face. If the photo is already within fal.ai's threshold, it MUST be sent as-is — no needless re-encoding.
- **FR-1617**: Photo-size reduction for fal.ai MUST happen on the backend, after upload and before the outbound fal.ai call, mirroring 003 FR-209. The user's visible Setup-form preview MUST NOT change as a side-effect (the reduction is internal).

**No-persistence and privacy**

- **FR-1618**: The backend MUST hold the user's photo bytes (original + any reduced variant prepared for fal.ai), the URL or bytes returned by fal.ai, and the composed text prompt only in process memory for the duration of a single Generate request — consistent with 001 FR-016 and 003 FR-215. None of these MUST be persisted to disk, database, cache, or application logs. Request/response logs MUST continue to redact photo payloads and any provider-side image URL.
- **FR-1619**: Sending the photo to fal.ai is inherent to running this provider and is accepted as the same scope choice 003 FR-216 made for Gemini. The backend MUST NOT send any user-identifying data to fal.ai beyond what is needed for generation: the photo bytes, the user's first name (already typed into the Setup form for the explicit purpose of personalising the poster), and the selection enums. No IP, email, account identifier, or analytics identifier MUST be attached to the fal.ai request. No additional consent dialogue is added at generation time; the Setup form remains the act of consent.
- **FR-1620**: Any error payload returned by fal.ai (including quota, safety-filter, queue, or authentication errors) MUST be logged on the backend in a form that does not include the photo bytes or the API key. The frontend-visible error MUST be the generic fallback notice (FR-1615) — not the raw provider error.

**Backwards compatibility**

- **FR-1621**: All existing Gemini behaviour (003) MUST remain in place without modification of its observable contract: when an operator runs the backend with the existing `gemini` profile and a Gemini key, the system behaves *exactly* as it does today — same response shape (now extended with `provider: "gemini"` per FR-1612, which is additive), same fallback semantics, same logging, same photo reduction, same poster composition. No existing test of the Gemini path MUST need to be rewritten because of this feature beyond accommodating the additive `provider` field on the response.
- **FR-1622**: The frontend MUST continue to function without code changes for the user-visible flow. It MUST be free to read the new `provider` field for diagnostic purposes (e.g. to log it during development) but MUST NOT surface it in the rendered UI for the end user. The user-visible UI for a fal.ai run MUST be indistinguishable from a Gemini run (success path) and MUST be indistinguishable from a Gemini-fallback run (failure path).

### Key Entities

- **ProviderSelection** *(new)* — the resolved choice of real image-generation provider for the running backend process. One of `gemini` | `falai` | `none` (the latter meaning "stub-only"). Resolved exactly once at process start from the active profile / configuration. Not request-scoped, not user-visible, not persisted.
- **GenerationOutcome** *(extended from 003)* — the structured value on the backend response. Its existing `outcome` (`"real"` / `"fallback"`) and conditional `reason` fields keep their 003 semantics; a new `provider` discriminator (`"gemini"` / `"falai"` / `"stub"`) is added per FR-1612, set on every response. Operator-visible only.
- **FalAiClient** *(new — conceptual)* — the seam through which the backend reaches fal.ai's `nano-banana-pro/edit` model. Conceptually parallel to today's Gemini client. Its concrete shape (Java SDK call vs raw HTTPS) is a planning decision; the spec only requires that it lives behind the same `ImageGenerator` abstraction the stub and Gemini paths already implement, so a single Generate orchestrator code path drives all three.
- **PhotoReductionResult (per provider)** *(extended from 003)* — the transient in-memory reduced photo. Already exists for Gemini; analogous instance produced for fal.ai when fal.ai is the selected provider, tuned to fal.ai's limits. Lives only for the duration of one request; never persisted; not surfaced to the user.

## Assumptions

- The model identifier referenced in the issue — `fal-ai/nano-banana-pro/edit` — is treated as the intended target. If that exact identifier is not reachable at fal.ai at implementation time (model name changes, new variant supersedes it), the planning phase selects the closest currently-reachable fal.ai image-edit model and records the substitution in `plan.md`. The spec is not invalidated by such a substitution because FR-1610 makes the identifier configurable.
- The configuration mechanism for switching providers is **Spring profiles** (`spring.profiles.active=falai` / `=gemini`), consistent with the issue's example and with the existing `gemini` profile already in `application.yml`. The default profile remains stub-only.
- fal.ai's Java integration page (linked from the issue) documents both an SDK and the underlying queue-based REST endpoints. The choice between using the published Java helpers vs raw HTTPS calls is a planning-phase decision constrained by the project's existing pattern (Gemini today is wired via raw `HttpClient` + Jackson — no Google SDK). Whatever choice is made MUST keep the integration testable without WireMock-equivalent infrastructure (mockable seam).
- The fal.ai API may be **asynchronous / queue-based** (request-id → poll-or-subscribe → result). Whatever the exact wire pattern, the backend serves the user's Generate as a **synchronous-from-the-frontend's-perspective** HTTP request (the existing `POST /api/generate` shape from 002 / 003 is preserved). The async machinery is hidden behind the backend; the frontend never sees a request-id.
- Photo-reduction parameters (max bytes, longest edge, JPEG quality) for fal.ai are tuned to fal.ai's published limits and may differ from Gemini's tuning. The planning phase records the chosen numbers; SC-1603 validates them.
- The user-facing UI **does not** gain a provider toggle, a model picker, or any visual indication of the selected provider. Provider selection is a backend / operator concern. The user is supposed to see the same product whether the run was served by Gemini, fal.ai, or the stub (modulo the existing fallback notice when applicable).
- The accent colour, character text (title / tagline / superpowers / quote), poster frame (015), and logo overlay (008) all continue to be produced by the existing pipeline. fal.ai is the source of the **central image only** — exactly the role Gemini's image side plays today. Character text continues to be produced by `GeminiCharacterGenerator` (014) when Gemini is configured for text; this feature does not introduce a separate fal.ai text path.
- The existing `outcome` / `reason` shape from 003 is preserved; the new `provider` field is purely additive to the response contract. Older clients (none in production for this POC, but conceptually) would still parse `outcome` and `reason` correctly.
- The constitution's Technology Standards (Java 21 / Spring Boot 3 backend, React 18+ TS strict frontend) and Principle-level accessibility + resilience requirements continue to apply. No new persistence layer is introduced (this remains a no-persistence POC per 001).
