# Feature Specification: Real (LLM-backed) Character Generator

**Feature Branch**: `014-real-character-generator`
**Created**: 2026-04-27
**Status**: Draft
**Input**: User description: "Substitute Stub Character Generator for the Real AI. Current implementation of the CharacterGenerator is a stub that takes values from a preset json file. This stub should be replaced with a logic that calls the LLM for the needed character 'traits' (tagline, title, superpowers, quote etc). Let's use Gemini for now, since we already use it for the image generation logic and can hopefully reuse the KEY. All the traits should be of a reasonable length (definitely no more than 100 characters each)."

Closes squer-solutions/ai-codecrafts-alterego#33.

## Clarifications

### Session 2026-04-27

- Q: How is the "≤ 100 characters" trait length measured? → A: NFC-normalised Unicode code points (matches the 011 firstName validator's rule).
- Q: What output language must the generated traits be in? → A: English only, regardless of `firstName` script or any browser hint.
- Q: What is the default character-call request timeout? → A: 15 s (text is faster than image; ~2× headroom over typical p95; image path's 25 s default is unchanged).
- Q: How should the user-supplied `firstName` be handled when it ends up inside the LLM prompt? → A: Trust the existing 011 `ValidFirstName` validator + FR-1407 shape parser; the prompt builder MUST NOT add a second sanitization layer.
- Q: Is per-process character-response caching/memoization allowed? → A: No — every Generate hits the LLM (subject to retries); no in-RAM cache, no LRU, no memoization across requests.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Receiving an LLM-authored character (Priority: P1)

A user fills in their first name, picks the five Setup categories (Pose, Archetype, Universe, Vibe, Art Style), and presses Generate. The poster they receive is captioned with character text — a hero title line, a tagline, three superpowers, and a quote — that has been authored on the fly by the LLM for *their specific* combination of inputs, rather than picked from a small fixed pool of hand-written variants. The text *feels* like it understands the chosen Archetype, Universe, and Vibe, not just the Archetype.

**Why this priority**: This is the entire feature. Without it, two users with different (Archetype × Universe × Vibe × Art Style × First Name) tuples can still get character lines drawn from the same four hand-written variants — the text part of the poster does not actually reflect the user's choices the way the image does. Replacing the stub is the whole point.

**Independent Test**: With a configured LLM provider, run a single Generate request and inspect the response: the `heroTitleLine2`, `tagline`, three `superpowers`, and `quote` MUST be different from the hand-written stub fixtures for that Archetype, AND MUST visibly reference at least one Setup category beyond the Archetype itself (e.g. the chosen Universe or Vibe is recognisably echoed in the wording).

**Acceptance Scenarios**:

1. **Given** the backend is configured for the real LLM and the user has selected a complete Setup, **When** they press Generate, **Then** the returned `GeneratedCharacter` is generated by the LLM (not loaded from `stubs/characters.json`) and is rendered onto the poster exactly the way stub-generated text was rendered before.
2. **Given** two requests with the same five Setup choices but different first names, **When** both complete successfully, **Then** the `heroTitleLine1` reflects each respective first name uppercased, exactly as the stub already does.
3. **Given** two requests that differ only in `universe` (Archetype/Vibe/Pose/Art Style/First Name held constant), **When** both complete successfully, **Then** the resulting `heroTitleLine2`, `tagline`, `superpowers`, or `quote` differ in at least one trait — i.e. the LLM is conditioning on Universe, not just on Archetype.
4. **Given** a user with a complete Setup, **When** Generate succeeds, **Then** the response shape and field names returned to the frontend are byte-compatible with what the stub used to return (same `heroTitleLine1` / `heroTitleLine2` / `tagline` / `superpowers` / `quote` keys, same surrounding `AlterEgoResponse` envelope, same `meta.outcome` semantics) so no frontend change is required for the happy path.

### User Story 2 — Honest fallback when the LLM call fails (Priority: P1)

If the LLM provider is unreachable, times out, returns a malformed payload, refuses on safety grounds, runs out of quota, or is simply not configured (no API key), the user still gets a complete poster. The orchestrator's existing fallback contract — "always return a poster, with `meta.outcome=fallback` and a typed `meta.reason`" — applies to character-text failures exactly the way it already applies to image failures.

**Why this priority**: The product's hard rule (001 FR-018, restated by 003) is that *every* `/api/generate` request resolves to a complete poster. Swapping a deterministic local stub for an external HTTP call without preserving that guarantee would be a regression. Fallback is therefore P1, not a "nice to have".

**Independent Test**: Force the LLM call to fail (no API key configured, or the `force-stub-failure` profile, or pointing the endpoint URL at an invalid host). Submit a Generate request. The response MUST still be a `200 OK` `AlterEgoResponse` carrying `meta.outcome=fallback`, a non-null `meta.reason`, and a complete character + poster pair. The `correlation-id` MUST be set as today.

**Acceptance Scenarios**:

1. **Given** the LLM provider is not configured (e.g. blank API key), **When** Generate is invoked, **Then** the system MUST NOT attempt an outbound call, MUST return `meta.outcome=fallback` with `meta.reason=not_configured`, and MUST still emit a complete character + poster.
2. **Given** the LLM provider is configured but the call fails (network error, timeout, 5xx, 429, malformed body, safety refusal), **When** Generate is invoked, **Then** the system retries per the existing retry policy and, on final failure, returns `meta.outcome=fallback` with the appropriate typed reason (`network_error`, `timeout`, `rate_limited`, `malformed_response`, or `safety_refused`).
3. **Given** the `force-stub-failure` profile is active (used by E2E tests for SC-004), **When** Generate is invoked, **Then** the response is a fallback poster within the same time budget that previously satisfied SC-004 ("≤ 5 s to fallback poster when stubs fail").
4. **Given** a fallback response is returned, **When** the operator inspects the structured logs, **Then** exactly one `event=generation.completed outcome=fallback reason=<wire>` line is emitted with the active `correlationId`, in the same shape today's image-fallback logs use.

### User Story 3 — Trait shape and length stay safe for the existing poster layout (Priority: P1)

The poster's text layout was designed around the stub fixtures' rough sizes — short, punchy lines. The LLM's output must respect those budgets so the rendered poster does not break visually (lines wrapping into the photo, taglines spilling off the page, superpowers list overflowing). Each trait the LLM produces must be of a reasonable length: no single trait longer than 100 characters, and the trait set as a whole must be the canonical shape (one title line, one tagline, exactly three superpowers, one quote).

**Why this priority**: A 250-character "tagline" or four superpowers would render the poster broken in production. The whole frontend assumes the existing shape. P1 because shape is part of the contract — it is not enough for the text to be "creative", it must also be drop-in.

**Independent Test**: Run 50 generations with a deterministic seed (or a recorded provider transcript) and assert that for every response: (a) every trait string is ≤ 100 characters after trimming, (b) the `superpowers` list contains exactly 3 entries, (c) every trait is non-empty, non-whitespace, and (d) the `heroTitleLine1` is the user's first name uppercased.

**Acceptance Scenarios**:

1. **Given** any successful LLM response, **When** the response is materialised into a `GeneratedCharacter`, **Then** `heroTitleLine2`, `tagline`, every `superpowers[i]`, and `quote` are each non-blank and ≤ 100 characters in length.
2. **Given** any successful LLM response, **When** the response is materialised, **Then** `superpowers.size() == 3`.
3. **Given** the LLM returns a response with too many or too few superpowers, with overlong traits, or with a missing trait, **When** the orchestrator tries to materialise it, **Then** it is treated as `malformed_response` and the fallback path runs (US 2).
4. **Given** the user typed `paula`, **When** the LLM responds, **Then** the final `heroTitleLine1` rendered to the user is `PAULA`, regardless of what casing or formatting (if any) the LLM produced for the name — i.e. the first-name → uppercased-first-name substitution remains owned by our code, not the LLM.

### User Story 4 — Operator-controlled rollout, with the deterministic stub still available (Priority: P2)

A backend operator (or a CI/E2E test) needs a reliable way to choose between "real LLM character generator" and "deterministic stub character generator" without changing code. The mechanism should mirror the one image generation already uses (a Spring profile + an API key check), so a developer who already understands the 003 setup understands this one.

**Why this priority**: P2 because the feature works for end users with a single mode, but it is operationally important: integration tests, E2E tests, and the SC-004 fallback assertion all rely on a deterministic, non-network text path. Reusing the existing profile pattern keeps cognitive load on the team low.

**Independent Test**: Start the backend with `SPRING_PROFILES_ACTIVE=default` (or no profile) and verify Generate returns text from the existing fixture-driven stub. Restart with `SPRING_PROFILES_ACTIVE=gemini GEMINI_API_KEY=<key>` and verify Generate returns LLM-authored text. Restart with `SPRING_PROFILES_ACTIVE=gemini` but no key — Generate returns a fallback with `meta.reason=not_configured`. Restart with `SPRING_PROFILES_ACTIVE=force-stub-failure` and verify both image and character paths trigger the fallback (existing SC-004 contract holds).

**Acceptance Scenarios**:

1. **Given** the `default` profile, **When** Generate is invoked, **Then** the deterministic fixture-driven `StubCharacterGenerator` answers (zero outbound HTTP from the character path).
2. **Given** the `gemini` profile with a valid API key, **When** Generate is invoked, **Then** the LLM-backed character generator answers and the stub is not consulted on the happy path.
3. **Given** the `gemini` profile but no API key, **When** Generate is invoked, **Then** the character path fails fast pre-HTTP with `not_configured` and the orchestrator falls back, in lockstep with how image generation already behaves under the same condition.
4. **Given** the `force-stub-failure` profile, **When** Generate is invoked, **Then** the existing `ForceFailureCharacterGenerator` (or its successor with identical effect) still throws and the fallback poster is still served — i.e. SC-004 is preserved by this feature.

---

### User Story 5 — Reuse one Gemini API key across image and character paths (Priority: P3)

The operator should not need to manage two separate Gemini API keys for one product. If `GEMINI_API_KEY` is configured, both the image generator and the character generator pick it up. The character path may reuse the same `aiavatar.gemini.*` configuration block, with character-specific knobs (model id for text, request timeout, etc.) added alongside the existing image-specific knobs rather than duplicated under a separate top-level prefix.

**Why this priority**: P3 because it is an ergonomics decision, not a correctness one — but it is the explicit ask in the issue ("can hopefully reuse the KEY") and it materially simplifies operation.

**Independent Test**: Set `GEMINI_API_KEY=…` once in the environment and confirm both the image path (003) and the new character path read it. Override only the text-side model id and confirm only the text path's model selection changes.

**Acceptance Scenarios**:

1. **Given** a single environment variable `GEMINI_API_KEY` is set, **When** the backend starts under the `gemini` profile, **Then** both the image generator and the character generator are configured (no second key required).
2. **Given** the operator wants the text and image paths to use different models, **When** they set the text-model-id override and the image-model-id override independently, **Then** each path reads its own model id and they do not interfere.

### Edge Cases

- **Provider returns valid prose but in the wrong shape** (e.g. a single paragraph instead of structured fields, or four superpowers, or a JSON object with extra keys / missing keys). Treated as `malformed_response`; orchestrator falls back. The character generator MUST NOT silently truncate to three superpowers or invent missing traits — the request fails into fallback.
- **Provider returns text with one trait > 100 characters.** Treated as `malformed_response` (length is part of the shape contract — see US 3). Truncating mid-word would corrupt the LLM's voice; falling back is honest.
- **Provider produces output that includes the user's first name** in `heroTitleLine2` / `tagline` / `quote`. Acceptable — the LLM is allowed to address the user; only `heroTitleLine1` is owned by our substitution.
- **Provider safety-refuses on a benign first name** (e.g. a name string that happens to share characters with a flagged token). Treated as `safety_refused`; orchestrator falls back. This is consistent with how 003 already handles image-side safety refusals.
- **Two simultaneous requests with identical inputs.** No requirement that LLM output be identical run-to-run (the stub was deterministic; the LLM is not). Both responses must individually satisfy US 3's shape rules; they need not be byte-identical. Caching of any form (request-level, in-process LRU, memoization across requests) is explicitly forbidden by FR-1420 — every Generate hits the LLM.
- **Zero-latency cancellation by the user.** Out of scope — the existing endpoint is not cancellable today; this feature does not introduce cancellation. Network timeout still applies.
- **Outbound call breaches the request-level timeout** while the image call is still in flight. The orchestrator's existing per-call retry / timeout logic applies independently to the character call; one failing does not necessarily cancel the other in flight, but on final failure of either, the response uses the fallback path with the appropriate reason. (Whether character and image are issued sequentially or in parallel is a planning decision; user-visible behaviour is unchanged either way.)
- **A future feature wants to A/B real-vs-stub at request time.** Out of scope — this feature ships only the operator-level (profile-level) toggle. Per-request switching can be designed later without changing this contract.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-1401**: The system MUST provide a real, LLM-backed implementation of the existing `CharacterGenerator` seam (the contract `(AlterEgoRequest) → GeneratedCharacter`). The seam itself MUST NOT change shape — the orchestrator, the fallback provider, and the response model are unaffected.
- **FR-1402**: The LLM-backed character generator MUST be selected by configuration, mirroring the image generator's existing pattern: an explicit Spring profile (e.g. `gemini`) AND a non-blank API key. Without those, the path MUST NOT activate.
- **FR-1403**: When the LLM-backed character generator IS active and the API key IS blank, the generator MUST fail fast pre-HTTP with `FallbackReason.NOT_CONFIGURED`, exactly as `GeminiImageGenerator` does for the image path today.
- **FR-1404**: The deterministic fixture-driven `StubCharacterGenerator` MUST remain available under the `default` profile so unit / integration / E2E tests can run without an outbound call. Likewise, `ForceFailureCharacterGenerator` (or an equivalent) MUST remain wired under the `force-stub-failure` profile so SC-004 stays end-to-end testable.
- **FR-1405**: The LLM-backed generator MUST consume the user's full Setup tuple (Pose, Archetype, Universe, optional Vibe, Art Style, First Name) when composing its prompt, so changes to any axis can produce different traits. The prompt composition MUST be implemented as a stateless, unit-testable pure function (mirroring the 003 `GeminiPromptBuilder` pattern).
- **FR-1406**: The LLM response MUST be parsed into a `GeneratedCharacter` with these guarantees. "Length" is measured in **NFC-normalised Unicode code points after trimming surrounding whitespace** (the same canonical unit the 011 `ValidFirstName` validator uses for `firstName`, so the codebase has one consistent measurement rule):
    - `heroTitleLine2`: non-blank, ≤ 100 code points.
    - `tagline`: non-blank, ≤ 100 code points.
    - `superpowers`: a list of EXACTLY 3 non-blank entries, each ≤ 100 code points.
    - `quote`: non-blank, ≤ 100 code points.
- **FR-1407**: If any FR-1406 guarantee is violated by the provider's response, the parsing step MUST throw `GenerationFailure(MALFORMED_RESPONSE, …)` so the orchestrator's existing fallback path runs. The generator MUST NOT silently truncate, pad, or fabricate missing fields.
- **FR-1408**: `heroTitleLine1` in the final `GeneratedCharacter` MUST be `firstName.trim().toUpperCase(Locale.ROOT)`, regardless of what the LLM emitted for the name. Whatever the LLM produced for `heroTitleLine1` (if anything) is discarded — name substitution is owned by our code.
- **FR-1409**: The character path MUST integrate with the existing retry policy used by `AlterEgoService` (the constitutionally-mandated `RetryTemplate`, Principle IV). Transient failures (timeout, 5xx, 429, network) MUST be retried per the active policy. Non-transient failures (`MALFORMED_RESPONSE`, `SAFETY_REFUSED`, `NOT_CONFIGURED`) are surfaced as `RuntimeException` and therefore also retry under the same default policy — these retries are wasteful but harmless because the failure mode is deterministic, mirroring 003's image-side posture (specialising the retry policy per reason was deliberately rejected during planning, see `research.md` §R5, to keep the retry surface symmetric with the image side and to avoid expanding the policy code for no user-observable gain). The orchestrator's outer fallback path runs after retries are exhausted regardless of which class of failure occurred.
- **FR-1410**: Provider-boundary failures from the character path MUST be classified into the existing `FallbackReason` enum (`NOT_CONFIGURED`, `NETWORK_ERROR`, `RATE_LIMITED`, `TIMEOUT`, `MALFORMED_RESPONSE`, `SAFETY_REFUSED`) using the same mapping table 003 established for the image path. The enum MUST NOT be extended by this feature — if the LLM exposes a new failure mode that does not fit, the closest existing reason MUST be used (consistent with the catch-all in `AlterEgoService`).
- **FR-1411**: Exactly one structured log event (`event=generation.completed`, `outcome` ∈ {`real`, `fallback`}, optional `reason`, `correlationId`) MUST be emitted per request, exactly as today. This feature MUST NOT introduce a second log event for character-vs-image (the existing single-event contract is preserved).
- **FR-1412**: The character path MUST NOT introduce any new persistence — the request payload, the prompt, the LLM response body, and the parsed traits MUST live only in process memory for the duration of the request. This extends 001 FR-016 / FR-017 / FR-024 unchanged.
- **FR-1413**: Logs MUST NOT include the user-supplied `firstName`, the photo, or the raw LLM response body in plain text. The same redaction posture that already applies to the photo (003) applies here to the prompt + LLM response. Existing structured-args helpers (`StructuredArguments.kv`) are the only allowed channel.
- **FR-1414**: The Gemini API key MUST be reusable across the image path and the character path — a single environment variable (today's `GEMINI_API_KEY`) MUST configure both. Where the two paths need to differ (e.g. model id, request timeout), each path's override MUST be independent so changing one does not implicitly change the other.
- **FR-1415**: The wire shape returned to the frontend (the `character` object inside `AlterEgoResponse`, with keys `heroTitleLine1`, `heroTitleLine2`, `tagline`, `superpowers`, `quote`) MUST NOT change. No frontend change is required by this feature; existing 002–013 frontend code reads the response unchanged.
- **FR-1416**: Existing OpenAPI contract tests, `RecordInvariantsTest`, and `StubCharacterGeneratorTest` MUST continue to pass unchanged — this feature MAY ONLY *add* new tests (real-path unit tests, prompt-builder tests, response-parser tests, integration tests under the `gemini` profile).
- **FR-1417**: Outbound LLM calls MUST be subject to a request-level timeout configured the same way the image path's is configured (env-var-overridable). The default value MUST be **15 seconds** (env-var-overridable, e.g. via `GEMINI_TEXT_REQUEST_TIMEOUT_MS` or the equivalent the plan settles on). The image path's existing 25 s timeout is **unchanged** by this feature. The 15 s default is calibrated against typical Gemini text-model end-to-end latency (~2–8 s) with ~2× headroom; SC-1409's "no regression beyond the configured character-call timeout" is therefore bounded at 15 s above the pre-feature baseline by default.
- **FR-1418**: All four generated traits (`heroTitleLine2`, `tagline`, every `superpowers[i]`, `quote`) MUST be authored in **English**, regardless of the script of the user-supplied `firstName` and regardless of any browser-locale hint that may be sent in future. This pins consistency with the English UI chrome (numbered steps, "Generating your alter ego…" copy, fallback poster copy, image prompt) so a single user does not see half of the poster in one language and half in another. The prompt builder MUST instruct the LLM to respond in English; if the LLM nonetheless returns traits in a non-English language, this is a `MALFORMED_RESPONSE` per FR-1407 (i.e. enforced at the parser, not just suggested in the prompt — though detection MAY be heuristic and is not required to identify every possible non-English string; the prompt instruction is the primary defence).
- **FR-1419**: The character prompt builder MUST interpolate the user-supplied `firstName` into the prompt **without** an additional sanitization or escaping pass beyond what the 011 `ValidFirstName` validator already enforces at the controller boundary (NFC code-point ≤ 50, restricted Unicode subset of letters / spaces / hyphens / apostrophes). The prompt-injection defence model is: (a) input is bounded by 011 at the controller, (b) prompt-injection attempts that survive 011 are caught by FR-1407's shape parser (a "haiku in three superpowers" violates the trait shape and routes to fallback), and (c) Gemini's own safety filters provide a third layer surfaced as `SAFETY_REFUSED` per FR-1410. No fourth, character-generator-local sanitization layer is required or permitted — duplicating 011 here would create two divergent definitions of "valid first name" without measurably improving safety.
- **FR-1420**: The character path MUST NOT introduce caching, memoization, or any other reuse of a previously-computed `GeneratedCharacter` across requests. Every successful Generate request that reaches the LLM-backed generator MUST result in a fresh outbound LLM call (subject only to FR-1409's `RetryTemplate` retries within a single request). This extends the no-persistence posture to in-RAM "soft persistence": no LRU, no per-process cache, no per-session cache, no per-(request-tuple) memoization. A future feature MAY introduce caching with its own threat model, TTL, and per-user isolation story; this feature explicitly does not.

### Key Entities

- **Real character generator**: A new `CharacterGenerator` implementation, active under the `gemini` profile, that calls the LLM provider, parses the response into a `GeneratedCharacter`, and throws `GenerationFailure` on any provider-boundary failure. Pure orchestration; does not own retry, fallback, or logging — those belong to `AlterEgoService` exactly as today.
- **Character prompt builder**: A stateless component that maps `AlterEgoRequest` to a textual prompt instructing the LLM to produce the four required traits in a parseable shape, with the explicit ≤ 100-character-per-trait constraint and the "exactly three superpowers" constraint baked in. Mirrors the role 003's `GeminiPromptBuilder` plays for image prompts.
- **LLM response parser**: A stateless component that converts the LLM's raw response body into a `GeneratedCharacter`, enforcing FR-1406's guarantees and surfacing violations as `GenerationFailure(MALFORMED_RESPONSE)`. Owns the "what counts as well-formed" judgement so it can be unit-tested with recorded transcripts.
- **Provider configuration (extended)**: The existing `aiavatar.gemini.*` configuration block, augmented with text-side knobs (e.g. text model id, text request timeout) where they need to be tunable independently of the image-side knobs. The `api-key` field is shared.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-1401**: With the LLM provider configured and reachable, ≥ 95% of Generate requests over a soak run return `meta.outcome=real` with character text authored by the provider (i.e. the real path is the dominant path on the happy path, not the fallback).
- **SC-1402**: 100% of returned `GeneratedCharacter` objects — real path, fallback path, every test fixture — satisfy the shape contract: 4-trait set, exactly 3 superpowers, every trait ≤ 100 characters, every trait non-blank.
- **SC-1403**: 100% of provider-boundary failures (forced via fault-injection or observed naturally) are surfaced as `meta.outcome=fallback` with a typed `meta.reason` from the existing `FallbackReason` enum. Zero unhandled exceptions escape `AlterEgoService` to the controller layer.
- **SC-1404**: SC-004 from 001 is preserved unchanged: under the `force-stub-failure` profile, a Generate request returns a fallback poster end-to-end within ≤ 5 seconds (median).
- **SC-1405**: Under the `default` profile and existing test suites, every pre-existing test continues to pass with no modification to the test code itself (the stub generator's behaviour, including the SHA-256-driven determinism, is byte-preserved).
- **SC-1406**: The wire response of `/api/generate` (response body keys, types, value shapes) is byte-compatible with the pre-feature contract for the happy path: a recorded fixture from before this change deserialises identically against the post-change OpenAPI schema.
- **SC-1407**: Across a 100-sample soak with five distinct (Archetype, Universe, Vibe) combinations under the real path, the *cross-combination* trait pool — i.e. the set of unique `heroTitleLine2` values produced — is strictly larger than the cross-combination pool a fixture-driven stub would have produced for the same inputs (≤ 6 archetypes × ≤ 4 variants = 24 distinct line-2 values today). This is the operational measure of "the LLM is actually doing something the stub couldn't".
- **SC-1408**: Operator can flip between real-path and stub-path (and vice versa) with a single profile + env-var change — no code change, no rebuild, no schema migration.
- **SC-1409**: The worst-case 95th-percentile wall-clock latency of a successful Generate request does not regress by more than **15 seconds** (the default character-call timeout configured by FR-1417) above its pre-feature baseline. The budget the user "spends" on character generation is bounded by config, not hidden — and an operator who tightens or relaxes the timeout shifts this bound accordingly.

## Assumptions

- The provider used is Gemini, reusing the existing `aiavatar.gemini.*` configuration block and the `GEMINI_API_KEY` env var. A different provider could be substituted later without spec amendment because the contract this feature pins is the seam and the failure model, not the vendor.
- The character call uses Gemini's text-generating model family (e.g. a `gemini-*-flash` text model) with a JSON-shaped response so the parser can validate the four-trait shape mechanically. Exact model id, prompt template, and response format are planning decisions, not spec decisions — but the planning MUST land on a shape that the response parser can validate against FR-1406 *without* heuristic prose extraction (e.g. structured JSON output, or a tightly-templated wrapper format the parser can recognise unambiguously).
- The character call and the image call are issued by the same orchestrator (`AlterEgoService`) inside the same request handler. Whether they run sequentially or in parallel is left to the implementation plan; this spec only requires that overall request latency does not regress beyond the configured per-call timeout (SC-1409).
- The existing `RetryTemplate` policy, structured-log event shape, and `FallbackReason` enum are reused as-is — they were designed in 003 to be provider-agnostic at the seam level and this feature does not need to extend them.
- The `force-stub-failure` profile continues to apply to *both* generators (image and character) at the same time. This is the simplest interpretation of the existing SC-004 contract; if a future feature needs to fail one path independently, it can introduce more profiles without breaking this one.
- `RecordInvariantsTest`, `StubCharacterGeneratorTest`, and the OpenAPI contract tests continue to be the regression net for the pre-feature surface area; this feature only *adds* tests around the new components.
- No persistence — extending 001 FR-016 / FR-017 / FR-024 unchanged. The prompt, the LLM response, and the parsed traits all live only in process memory for one request.
- This feature does not change the frontend. The TypeScript types for `AlterEgoResponse.character` continue to map onto the same five fields; the rendering code in `AlterEgoPage` / `Poster` / `ResultMeta` is not touched. Any frontend side-effects (e.g. showing a banner on `outcome=fallback`) already exist from 003 and continue to apply unchanged.
