# Feature Specification: Default outbound email to Namecheap PrivateEmail

**Feature Branch**: `027-privateemail-smtp`
**Created**: 2026-05-19
**Status**: Draft
**Input**: User description: "Configure mailing server to be the namecheap.com mailing server (which is privateemail). This mailing server should be used to send the generated alter ego images to the given email address by clicking 'Send as email' button on the second tab of the app."

## Clarifications

### Session 2026-05-19

- Q: How should the From / sender address be supplied? Auto-derive from the authenticated SMTP username, operator-supplied explicitly, or shipped as a default? → A: Operator-supplied explicitly, sourced from Terraform variables wired into the deployment's environment. The same From value is used for every send in a given deployment (not per-user, not derived). A missing From is a not-configured condition (i.e., From joins host + username + password in the configured-check).
- Q: How should the app react to PrivateEmail rate-limit responses (per-mailbox / per-window submission limits)? → A: No special handling. Expected load is effectively zero; the simplest config wins. The 023 retry budget (5 attempts, exponential backoff with jitter) applies uniformly to every SMTP error, rate-limit-shaped or not. No client-side throttling, no rate-limit-aware fast-fail, no per-session limiter.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Out-of-the-box: app ships pre-pointed at PrivateEmail, only credentials needed (Priority: P1)

An operator deploys the application. They want emails generated by the Alter Ego tab's **Send as Email** button to be delivered through Namecheap's **PrivateEmail** mail service. Today, the SMTP seam built in feature 023 ships with a blank default mail-server target — the operator has to set the host, port, encryption mode, credentials, *and* sender address before the app will deliver. This feature changes the defaults so the operator only needs to supply the secrets (mailbox credentials + sender address); the host, port, and encryption mode that PrivateEmail expects are baked into the application's shipped configuration.

**Why this priority**: This is the entire feature. Without it, the operator has to research PrivateEmail's connection parameters themselves and translate them into application config. The point of the change is to make "deliver via PrivateEmail" the path of least resistance — the default, not an exotic configuration.

**Independent Test**: Deploy the app with only the three credential-shaped env vars set (mailbox username, mailbox password, sender address). Generate an alter ego, enter a recipient email, click Send as Email. Observe the email arriving in the recipient mailbox, delivered through PrivateEmail's SMTP infrastructure, with the existing 023 subject/body/attachment unchanged. No other configuration changes were required.

**Acceptance Scenarios**:

1. **Given** the application is deployed with the mailbox-username and mailbox-password env vars set (and a sender address supplied), **When** a user clicks Send as Email after a successful generation, **Then** the message is delivered via Namecheap PrivateEmail's SMTP service to the recipient with the existing 023 FR-2313 subject and FR-2314 body and the generated image as attachment.
2. **Given** the application is started with no operator overrides at all, **When** any caller queries the running app's effective mail-server configuration (logs at startup, actuator info, runbook check), **Then** the host points at PrivateEmail's documented SMTP endpoint, the port is the encrypted-submission port appropriate for PrivateEmail, and authentication + transport-encryption are enabled — i.e., the defaults are a working PrivateEmail recipe, not a placeholder.
3. **Given** the operator wants to direct mail to a different SMTP provider (e.g., a local dev relay, an alternate paid provider), **When** they set the existing host/port/protocol env vars to that provider's values, **Then** the application uses those values and the PrivateEmail defaults are completely overridden — no PrivateEmail-specific behaviour is hard-coded anywhere except as defaults.

### User Story 2 - Operator forgot to supply credentials → clear "not configured" signal (Priority: P1)

An operator deploys the application but has not yet provisioned a PrivateEmail mailbox (or has not yet plumbed the credentials into the deployment). They open the app and click Send as Email expecting *something* to happen.

Today (023), "configured" is decided purely by whether the mail-server host is non-blank. With PrivateEmail's host now baked in as the default, that 023 rule would say "configured" the moment the app starts — even though no credentials exist — and the click would surface a confusing retryable-failure alert (the existing 023 FR-2316 path). This story is about preserving the helpful "not yet configured" alert (023 FR-2311) for that misconfiguration case.

**Why this priority**: This is the difference between an operator hitting a helpful "not yet configured — set these env vars" signal versus a misleading "send failed, retry" loop. Both paths exist today; this story decides which one fires when credentials are missing while the new default host is present.

**Independent Test**: Deploy the app with **no** SMTP-related env vars supplied at all. Click Send as Email. Observe the existing 023 not-configured alert ("the email server is not yet configured") — not the 023 retryable-failure alert. Then supply only the username env var, restart, click again — still not-configured. Then supply both username and password, restart, click — the alert path changes and the send is attempted.

**Acceptance Scenarios**:

1. **Given** the application is started with the new default host (PrivateEmail) but with the mailbox-username env var blank, **When** the user clicks Send as Email, **Then** the existing 023 "email server is not yet configured" alert fires; no SMTP connection is attempted.
2. **Given** the application is started with the new default host (PrivateEmail) and a non-blank username but a blank password, **When** the user clicks Send as Email, **Then** the existing 023 "email server is not yet configured" alert fires; no SMTP connection is attempted.
3. **Given** the application is started with the new default host (PrivateEmail), non-blank username, non-blank password, **When** the user clicks Send as Email, **Then** the existing 023 send pipeline runs end-to-end (the not-configured short-circuit does NOT fire); if PrivateEmail rejects the credentials at click time, the existing 023 retryable-failure alert (FR-2316) fires.
4. **Given** the operator has explicitly cleared the host env var to the empty string (intentionally disabling email), **When** the app starts, **Then** the not-configured state is reported, exactly as the 023 baseline behaviour — i.e., explicit-blank-host still wins over the new default.

### User Story 3 - Documented runbook for setting up the PrivateEmail credentials (Priority: P2)

An operator unfamiliar with the project needs to wire a real PrivateEmail mailbox into a deployment. They want a single short runbook that tells them: which mailbox to provision in Namecheap PrivateEmail, which env vars to set, what the From-address must align with for PrivateEmail to accept the outbound message, and how to test it without sending to a real participant.

**Why this priority**: P2 because it accelerates the operator path but the running app still works without it as long as the operator already knows PrivateEmail's conventions. P1 stories deliver the technical change; this story closes the loop on knowledge transfer.

**Independent Test**: Read the runbook cold; follow it step-by-step in a test environment; the operator successfully sends a test email to their own address within 15 minutes without referring to PrivateEmail's external documentation or to the spec for 023.

**Acceptance Scenarios**:

1. **Given** the feature folder contains a runbook (`quickstart.md` or equivalent), **When** the operator reads it, **Then** it names the env vars to set (mailbox username, mailbox password, sender address), names PrivateEmail's connection parameters that are now baked in as defaults, and explains the From-address alignment rule that PrivateEmail enforces (the From header must be the authenticated mailbox or one of its aliases — otherwise PrivateEmail rejects the send at SMTP time).
2. **Given** the operator has followed the runbook, **When** they perform the documented smoke-test send, **Then** the test email arrives, confirming end-to-end wiring.

### Edge Cases

- **Credentials present but wrong**: PrivateEmail rejects at SMTP AUTH time. Surfaces as the existing 023 retryable-failure alert (FR-2316) after the existing project-wide retry budget exhausts. The "not configured" alert is reserved for the deploy-time misconfiguration case (Story 2).
- **From-address doesn't match the authenticated mailbox**: PrivateEmail rejects at submission time. This also surfaces as the 023 retryable-failure alert. The runbook (Story 3) calls out this constraint explicitly so the operator pre-empts it.
- **Operator wants to use a non-PrivateEmail provider**: Story 1 acceptance #3 — every PrivateEmail-shaped default is fully overridable via the existing env vars. No code change required.
- **Operator runs in a network where outbound submission ports are blocked**: surfaces as the existing 023 retryable-failure alert (FR-2316) — the click-time outcome is the same as for any other unreachable SMTP target. The runbook (Story 3) calls out the outbound port that must be reachable.
- **Operator sets credentials but the cached "configured" boolean was computed at a moment where one of them was still blank**: matches the existing 023 contract — the configured/unconfigured state is computed once at startup. A restart is required after credential changes. The runbook calls this out.
- **No new tab, no new field, no new button**: the entire user-facing surface (the Setup tab's Email field, the Alter Ego tab's Send as Email button, the alert popups) is unchanged from 023 and 025. Operators verify behaviour from the existing UI.

## Requirements *(mandatory)*

### Functional Requirements

#### Default mail-server target

- **FR-2701**: The application MUST ship with default outbound-mail configuration values that, taken together, target Namecheap **PrivateEmail's** SMTP submission service. The shipped defaults MUST cover the mail-server host, the encrypted-submission port appropriate for PrivateEmail, and the transport-encryption + authentication settings PrivateEmail requires for submitted mail — so that an operator supplying *only* mailbox credentials + sender address gets a working delivery channel.
- **FR-2702**: The shipped defaults MUST NOT include any real mailbox credentials (username, password). Those MUST remain operator-supplied via the existing env-var pathway from 023, and MUST be absent from any file checked into source control (this is a no-secrets-in-repo restatement, not a new policy).
- **FR-2703**: The shipped defaults MUST NOT include a real From / sender address. The sender address MUST be **operator-supplied explicitly per deployment**, sourced from Terraform variables that the deployment pipeline wires into the running process's environment via the existing `AIAVATAR_EMAIL_FROM` env var (from 023). The application MUST NOT auto-derive From from the SMTP username, MUST NOT vary From per user / per send, and MUST NOT ship a placeholder From that looks deployable. A blank From at startup MUST be treated as a not-configured condition (see FR-2706).
- **FR-2704**: Every default introduced by this feature (host, port, encryption mode, authentication mode) MUST be individually overridable by the operator via the same env-var mechanism that 023 already established for these knobs. No new "lock-in" to PrivateEmail beyond the defaults themselves.
- **FR-2705**: Setting any of the host/port/encryption env vars to an empty string MUST be treated as an explicit operator decision to clear that default — i.e., explicit blank wins over the new shipped default. (This preserves the 023 ability to fall back to the not-configured path purely by clearing the host.)

#### Configuration-presence semantics

- **FR-2706**: The startup "configured" decision MUST require, at minimum, that all four of: (a) the mail-server host, (b) the mailbox username used to authenticate to PrivateEmail, (c) the mailbox password used to authenticate to PrivateEmail, and (d) the From / sender address (FR-2703) are non-blank. If any of the four is blank, the application MUST consider itself "not configured" for the lifetime of that running process, and clicks on Send as Email MUST surface the existing 023 "email server is not yet configured" alert without attempting any SMTP traffic. Rationale: with a non-blank host shipped as a default, the 023 host-only rule would incorrectly report "configured" for any deployment that had not yet supplied credentials or sender; conversely an operator-supplied sender (FR-2703) is mandatory for PrivateEmail to accept the submission, so it belongs in the same gate.
- **FR-2707**: A configured-but-credentials-rejected outcome (PrivateEmail says NO at AUTH or at MAIL FROM time) MUST continue to surface as the existing 023 retryable-failure alert (FR-2316), NOT as the "not configured" alert. The "not configured" alert is reserved for the startup-presence failure case (FR-2706).
- **FR-2708**: The "configured" decision MUST remain a one-shot evaluation at application startup (preserving 023 FR-2318) — no live probe of PrivateEmail at startup, no re-evaluation per click, no re-evaluation on config-file change without restart. Operator credential changes require a restart.

#### Behaviour preservation

- **FR-2709**: The user-facing surface MUST be unchanged from 023 + 025. No new tabs, no new fields, no new buttons, no new alerts beyond what 023 already specified. The Send as Email button on the Alter Ego tab, the optional Email field on the Setup tab (per 025), the not-configured alert, the retryable-failure alert, and the success alert remain exactly as before.
- **FR-2710**: The subject (023 FR-2313), body (023 FR-2314), attachment (the currently-displayed generated image), recipient-resolution rules (023 FR-2308 / FR-2309), and the project's no-persistence posture (023 FR-2320) MUST remain unchanged.
- **FR-2711**: When the application is configured and a send succeeds via PrivateEmail, the visible application behaviour (success alert, latency envelope, repeatability per 023 FR-2317) MUST be indistinguishable from a send via any other configured SMTP provider — i.e., the user does not see or experience "this came from PrivateEmail" specifically.
- **FR-2713**: The application MUST NOT introduce rate-limit-aware logic for PrivateEmail. Every SMTP error returned by PrivateEmail (rate-limit-shaped, transient, or otherwise) MUST flow through the existing 023 retry budget unmodified (5 attempts, exponential backoff with jitter); on retry exhaustion the existing 023 retryable-failure alert (FR-2316) fires. No client-side throttling, no per-session limiter, no fast-fail branch on specific PrivateEmail response codes. Rationale: expected production load is effectively zero; simpler config beats premature optimisation.

#### Operator documentation

- **FR-2712**: The feature folder MUST contain a short operator runbook that:
  (a) lists the env vars an operator MUST set to wire a PrivateEmail mailbox — explicitly including the From / sender env var (FR-2703) — and names the Terraform variables that the deployment pipeline wires through into those env vars,
  (b) names the PrivateEmail connection parameters that ship as defaults (so operators can sanity-check them against PrivateEmail's own documentation),
  (c) calls out PrivateEmail's From-address alignment requirement (the From header MUST be the authenticated mailbox or one of its aliases — PrivateEmail rejects otherwise),
  (d) describes how to perform a smoke-test send to verify end-to-end wiring,
  (e) calls out that restart is required after a credential change (FR-2708),
  (f) calls out the outbound submission port that must be reachable from the deployment network.

### Key Entities *(include if feature involves data)*

- **Mail-server target**: The combination of host, port, encryption mode, and authentication mode the application uses to relay outbound mail. Today (023) the host defaults to blank. After this feature, the host + port + encryption + authentication mode default to a working PrivateEmail SMTP submission recipe; the credentials + sender remain operator-supplied. Not user-editable from within the app; changes require a restart.
- **Configured state**: A boolean evaluated once at application startup. Today (023) it is true iff the host is non-blank. After this feature, it is true iff host AND mailbox-username AND mailbox-password AND From-address are all non-blank (FR-2706). Drives whether Send as Email attempts SMTP or surfaces the "not yet configured" alert.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-2701**: With only the mailbox-username, mailbox-password, and sender-address env vars supplied, a Send as Email click delivers the existing 023 message (subject + body + attachment) to the recipient mailbox via Namecheap PrivateEmail within the existing 023 latency envelope (5 s end-to-end excluding upstream provider latency).
- **SC-2702**: With **no** SMTP-related env vars supplied at deploy time, a Send as Email click surfaces the 023 "email server is not yet configured" alert in 100% of attempts — never the retryable-failure alert, never a silent no-op, never a confusing generic error.
- **SC-2703**: An operator unfamiliar with the codebase but familiar with PrivateEmail can take a fresh checkout, follow the feature's runbook (FR-2712), and complete a successful smoke-test send to their own mailbox in under 15 minutes.
- **SC-2704**: For an operator who wants to point the app at a non-PrivateEmail SMTP provider, switching providers requires only setting the existing host/port/encryption/credentials env vars — zero source-code changes — and the new provider is in effect on the next restart.
- **SC-2705**: Zero PrivateEmail credentials (username, password) appear in any file checked into source control after this feature ships — verified by inspection of the diff and of the repository's tracked files.
- **SC-2706**: The 023 / 025 user-facing surface (Setup-tab Email field with conditional rendering, Alter Ego-tab Send as Email button, three alert variants) is byte-identical before and after this feature — verified by inspecting the existing 023/025 component tests and Playwright flows continuing to pass without modification.

## Assumptions

- **PrivateEmail's published SMTP parameters are stable**: the spec assumes Namecheap's documented PrivateEmail submission host, port, and encryption recipe will not change underneath this deployment. The spec deliberately does not pin literal port numbers or hostnames in this document — those concrete values land in the plan and runbook. If PrivateEmail later changes them, the fix is to update the shipped defaults, not to redesign the feature.
- **STARTTLS on the standard encrypted submission port is the default**: where PrivateEmail offers multiple connection recipes (e.g., STARTTLS on 587 vs implicit-TLS on 465), the shipped default uses the more conventional opportunistic-TLS recipe (STARTTLS on the encrypted-submission port). The alternative recipe is reachable by the operator via the existing override env vars — see FR-2704. Planning will pick one and document the other.
- **A real PrivateEmail mailbox exists or will exist before the app sends in production**: provisioning the Namecheap mailbox itself (purchasing the mailbox plan, configuring DNS / MX records on the chosen domain, creating the mailbox user) is the operator's responsibility and is explicitly out of scope. This feature wires the *application* to talk to a PrivateEmail mailbox; it does not provision one.
- **No new mail-side capability is introduced**: this feature does not add scheduled sends, queueing, bulk sends, BCC, CC, reply-to chains, attachments other than the generated image, or any new outbound surface. The send pipeline is exactly 023's, pointed at a different default endpoint.
- **No-persistence posture is preserved**: extends 001 FR-016 / 023 FR-2320 unchanged. The recipient address, the message bytes, the attached image, and the PrivateEmail authentication credentials live only in process memory; nothing is logged or cached. (The audit-log line at successful send still carries only the correlation id, per the 023 implementation.)
- **Restart-on-config-change is acceptable**: extends 023 FR-2318 unchanged. Operator changes to host / port / encryption / credentials / sender require a restart to take effect; there is no hot-reload path.
- **No backward-compatibility shim for the 023 host-only "configured" rule**: this feature replaces the 023 host-only rule with a stricter host + credentials rule (FR-2706). There is no toggle to fall back to the old rule. Rationale: the old rule was only safe with a blank-host default; that default is gone after this feature.
- **No in-app UI for managing SMTP configuration**: extends 023 — the mail server is operator-controlled via deployment config; participants never see or touch it.
- **Single mail provider per deployment**: the app sends through one configured SMTP target at a time. No provider-fallback ladder, no per-recipient routing, no domain-based selection. Matches 023's single-seam model.
